## 4. Architecture

```
levelup-2027/
  src/
    app/                    # routes: (auth), home, calendar, tasks, assistant, money/*, goals, reviews, settings
      api/                  # route handlers: push subscribe, cron tick, export, health
    domain/                 # PURE logic, no I/O. 100% unit-tested.
      money/                #   cents math, roulette engine, allocation invariants
      payroll/              #   payday recurrence, early-deposit estimation, 3-paycheck detection
      calendar/             #   rrule expansion, exceptions, conflict detection
      modes/                #   work-mode rules (what to suppress)
      assistant/            #   rule-based briefing / check-in / reflection builders
      notifications/        #   slot planning, quiet hours, dedupe keys
    server/                 # I/O: Prisma repositories, services, transactions, auth, audit
    ui/                     # design system components
  prisma/                   # schema + migrations + seed (your confirmed config only, no fake records)
  public/                   # manifest, icons, sw.js
  tests/                    # unit / integration / e2e
```

Rules:
- The `domain/` layer is pure functions. That is where the money and date rules live, so they can be exhaustively tested without a database.
- The `server/` layer is the only code that writes. Every financial mutation runs in a DB transaction and writes an `AuditLog` row.
- Every query is scoped by `ownerId`, checked server-side. There are no client-trusted IDs.

## 5. Database design (summary — full draft in `prisma/schema.draft.prisma`)

All money is **integer cents** (`Int`; max ≈ $21.4M, which is ample). Date-only facts (paydays, tiles completed on a date) use `DATE`. Moments in time use `timestamptz`.

### 5.1 Identity and settings
`User`, `Passkey`, `Session`, `UserSettings` (timezone, wake/bed targets, notification times 06:00/17:00/21:00, quiet hours, lock-screen privacy level).

### 5.2 Calendar
- `CalendarEvent`: title, category, start/end (tz), all-day, `rrule` (nullable), description, reminders, `sourceType` + `sourceId` (unique together, so a generated event can never duplicate).
- `EventException`: `(eventId, originalStart)` unique; either *cancelled* or *override* (new times/title). This is how one DOC shift is changed without touching the series.
- DOC schedule = one recurring series, `FREQ=WEEKLY;BYDAY=SA,SU,MO,TU,WE`, 08:00–16:00 ET, starting 2027‑01‑01, with no end date.
- **Paydays are not stored as events.** The calendar reads `Payday` rows and renders them as virtual, read-only events linked to their payroll record. That way they can't duplicate, and editing payroll updates the calendar.

### 5.3 Work modes
`ModeSession` (NORMAL | OVERTIME | ACTIVATION | RECOVERY, startedAt, estimatedEnd, endedAt, linked event). The current mode is the open session. Mode changes are only proposed — the app never deletes or moves events silently.

### 5.4 Tasks and habits
`Task` (priority, due date/time, rrule, reminder, status OPEN/DONE/SKIPPED, parent for subtasks), `Habit`, `HabitCheckIn` (`(habitId, date)` unique). Habits are completed only by your explicit tap. Habits show "x of last 7 days" rather than streaks.

### 5.5 Payroll (shared by Payroll, Extra Paycheck Planner, Roulette, Ledger)
- `PaySchedule`: kind REGULAR | OVERTIME, `anchorOfficialDate`, `intervalDays` (14), `earlyDepositOffsetDays` (−1 regular, 0 overtime), `effectiveFrom`, `active`. Changing an anchor creates a new schedule version effective from a date.
- `Payday`: `(scheduleId, officialDate)` unique, `expectedDepositDate`, `holidayFlag`, `manualOverrideDate`, `status` EXPECTED | RECEIVED | ZERO | SKIPPED. Rows are materialized 18 months ahead. **Regeneration deletes or moves only rows with no confirmed deposit.**
- `IncomeDeposit`: the *only* thing that means money arrived. `paydayId` unique (one deposit per payday), kind REGULAR | OVERTIME | GIG | OTHER, `netCents`, `actualDepositDate`, notes. It is created only when you confirm it.
- `OvertimeShift`: date, start/end, breaks, hours, rate (from `CompensationRule`), expected gross, status WORKED → SUBMITTED → APPROVED → EXPECTED → RECEIVED / DISPUTED, `paydayId`. Gross estimates are never mixed with confirmed net.
- Extra-paycheck months are **computed** from `Payday` rows (count of REGULAR official dates per month ≥ 3), so they recalculate automatically when the schedule changes.

### 5.6 Shared ledger and allocations

```
IncomeDeposit (confirmed $)            ← the funding source
   └─ AllocationPlan  (kind: OVERTIME_ROULETTE | EXTRA_PAYCHECK | MANUAL; status DRAFT → APPROVED → PARTIAL → COMPLETED | CANCELLED; rngSeed; version)
        └─ AllocationLine (target: ROTH | FUN | DEBT_TILE | MOVING_TILE | SCHD_DAY | EMERGENCY | GOAL | UNALLOCATED;
                           tileId?, amountCents, status PLANNED → APPROVED → CONFIRMED | CANCELLED | REVERSED)
              └─ Payment (confirmed real-world transfer; idempotencyKey unique; reversesPaymentId for corrections)
```

Invariants are enforced in the database, not just the UI:
1. **No dollar allocated twice.** On approve, inside a transaction holding `SELECT … FOR UPDATE` on the deposit: `Σ(APPROVED + CONFIRMED lines across all plans for this deposit) ≤ deposit.netCents`. Drafts reserve nothing.
2. **No tile completed twice.** Partial unique index: `UNIQUE (tileId) WHERE status IN ('APPROVED','CONFIRMED')` on lines, and `UNIQUE (tileId) WHERE reversedAt IS NULL` on payments.
3. **No double confirmation.** `Payment.idempotencyKey` unique, and a confirmation retried from a double-tap or a flaky network returns the original row.
4. **Exact reconciliation.** Confirmed allocations + unallocated remainder = deposit net, checked by a `CHECK`-style verification query that runs in tests and on the Money dashboard.
5. **Nothing is ever erased.** Corrections are reversal rows plus new rows, and every mutation writes `AuditLog(before, after, actor, at)`.
6. **Regular vs overtime is kept separate** by `IncomeDeposit.kind` and enforced by plan kind: an EXTRA_PAYCHECK plan can only draw on a REGULAR deposit, and an OVERTIME_ROULETTE plan only on an OVERTIME deposit.

### 5.7 Challenges
- `Challenge`: kind DEBT | MOVING_OUT | SCHD, `selectionRule` BIG_FIRST_RANDOM_TOP_N | SEQUENTIAL, `topN` (10), `targetCents`, `status` SETUP_REQUIRED | ACTIVE | COMPLETE.
- `ChallengeTile`: `(challengeId, number)` unique, `amountCents`, `status` OPEN | COMPLETED, `provenance` LIVE | IMPORTED_VERIFIED | IMPORTED_PROVISIONAL.

Seeded from your confirmed configuration:
- **Debt:** `SETUP_REQUIRED`, balance blank, excluded from Roulette until you enter a balance and a tile mapping that reconciles to it.
- **Moving Out:** 141 tiles, $1 to $141, target **$10,011**.
- **SCHD:** 100 days, $1 to $100, target $5,050. Days 1–37 ($703) shown as **provisional** until you confirm or import them. Next day = 38.

### 5.8 Roth IRA and fun money
`RothYear` (taxYear, `limitCents` *entered by you* — never hardcoded, eligibility note), `RothContribution` (via Payment, with taxYear). `RouletteSettings` per source kind: Roth reserve ($100 overtime default, **off** by default for an extra regular paycheck), fun minimum ($50 overtime default), leftover destination, goal priority order, rotation pointer.

### 5.9 Notifications
`PushSubscription` (endpoint unique, keys, device label), `NotificationPreference`, `NotificationJob` (`dedupeKey` unique, e.g. `briefing:2027-04-02`; `fireAt`; category; status PENDING/SENT/SUPPRESSED/SNOOZED/FAILED; reason), `NotificationLog`.

### 5.10 Growth modules (Phase 5)
`Workout`/`ExerciseSet`/`BodyMetric`, `JournalEntry` (type PRAYER | GRATITUDE | REFLECTION | RELATIONSHIP | SPEAKING; encrypted body), `DatePlan`, `ImportantDate`, `GigSession` (gross excludes tips; tips separate; miles, fuel, estimated vehicle cost/mile, tax reserve %), `EducationItem`, `CareerItem`, `ContentSession`, `Goal` (horizon ANNUAL/QUARTER/MONTH/WEEK, optional link to a challenge so goal progress *reads* confirmed payments rather than duplicating them).

## 6. Roulette engine (pure, deterministic, testable)

```
propose(input, seed) → Proposal
input = { availableCents, sourceKind, settings, debtTiles[], movingTiles[], schdNextDays[], rotationPointer }
```
1. `available = deposit.net − Σ committed lines` (from the DB, under lock at approval time).
2. Reserve Roth (configurable; overtime default $100, capped at remaining annual room if a limit is configured).
3. Protect fun minimum (default $50).
4. If `available < roth + fun` → return `NEEDS_ADJUSTMENT` with options (reduce Roth, reduce fun, skip). The app never goes negative.
5. Fair rotation over active goals, starting at the rotation pointer: each round, each goal takes one item if affordable:
   - Debt / Moving Out: filter OPEN tiles ≤ remaining (and debt ≤ outstanding balance), sort descending, take the top N (10), pick uniformly at random using a **seeded PRNG**.
   - SCHD: next sequential day only if affordable. Days are never skipped.
   - Stop when a full round adds nothing.
6. Leftover goes to fun money (or unallocated, per setting). Display: **YOUR FREE MONEY: $X 😎**.
7. Output lines + the seed. **Reroll** = new seed, new draft. It writes nothing besides replacing the draft row.

Drafts are saved server-side (survive refresh). Approve → DB transaction with invariant checks. Confirm each line → `Payment` (idempotent) → tile COMPLETED.

## 7. Notifications on iPhone — real requirements

- iOS / iPadOS **16.4 or later**.
- App served over **HTTPS** (a public host is required; it cannot be a LAN IP).
- You must **Add to Home Screen** from Safari and open it from the Home Screen icon. Push does not work in a Safari tab.
- Permission must be requested from a tap inside the installed app (we'll add an "Enable notifications" button).
- Delivery goes through Apple's push service. No Apple Developer account or App Store listing is needed.
- **Status until proven:** "Not verified on your device." I will mark push as working only after you confirm a test notification arrives on your iPhone.

Defaults: three non-urgent pushes per day (06:00 / 17:00 / 21:00 ET). Optional pushes are suppressed during Overtime/Activation/Recovery and quiet hours. Lock-screen text is generic by default ("Your evening check-in is ready"), with no dollar amounts unless you opt in.
